# Phase 1.0a — Verified facts (code-traced + measured, 2026-10-04)

Every spec assertion cites `F§n`. Code facts quote `file:line` at commit 8a23bd4; measurements were run on the
demo host (4 vCPU, low load ~0.9) with `docs/phases/1.0a/measure/measure_lazy_unload.py`.

## Code facts

- **F§1 — Model loads at import.** `serve/app.py:25` builds `ZeroShotEnsemble(...)` at module import, so the
  process holds all 3 models from boot. `/health` reads `_CLF.model_names` (`serve/app.py:43`).
- **F§2 — Label cap.** `serve/app.py:24` `MAX_LABELS = 50`; `serve/app.py:38` enforces it in the Pydantic model
  (`max_length=MAX_LABELS`) → any request with > 50 labels is rejected with a 422 *validation* error before the
  handler runs. Banking77 (77), CLINC150 (151), HWU64 (64), MASSIVE (60), MTOP (113) all exceed it.
- **F§3 — Request normalisation.** `serve/app.py:48-53`: message `.strip()`; labels stripped, empties dropped,
  duplicates dropped keeping first occurrence. The frontend does the same before sending
  (`space/index.html:157-158`). Errors: empty message / < 2 distinct labels → `HTTPException(422, str)`
  (`serve/app.py:54-57`).
- **F§4 — Response construction.** `serve/app.py:58-67`: `member_and_ensemble_proba(message, range(K),
  label_texts=labels)`; labels ordered by descending probability (Python stable sort → ties keep input order);
  `distribution` rounded to 4 dp; `members[m].pick = labels[argmax(member m)]` with display names
  `["PrismNLI-0.4B","bge-large","bge-base"]` (`serve/app.py:26`).
- **F§5 — Ensemble math.** `quorum/ensemble.py:93-98`: each member → softmax over the K label scores; ensemble =
  geometric mean (mean of log-probs), renormalised. Each label is scored on its own (one NLI pair or one cosine per
  label), but the NLI runs in padded batches of 32 (`quorum/ensemble.py:49-53`), so order invariance is only
  *approximately* guaranteed by construction — measured for K=6 (F§11) and K=77 (F§15).
- **F§6 — Package import is light.** `quorum/__init__.py:8-9` and the module headers import only numpy/stdlib;
  torch/transformers are imported inside the member constructors (`quorum/ensemble.py`, `_NLIMember.__init__` /
  `_EmbedMember.__init__`). A process that imports `quorum` but never builds a member never imports torch (F§9).
- **F§7 — Frontend contract.** `space/index.html:168-173` POSTs `{message, labels}` to `/predict`, only checks
  `r.ok`, then reads `label`, `confidence`, `distribution`, `members`. Client abort after 40 s
  (`space/index.html:165`).
- **F§8 — Per-item benchmark predictions do not exist.** `results/*.json` hold aggregates only;
  `scripts/eval_zeroshot.py` writes aggregates only (its `rep` dict); a filesystem search found no per-item dumps;
  the research session confirmed its GPU runs did not persist them. → regenerated by the research session (GPU) and delivered via git.

## Measurements (same process, sequential)

- **F§9 — Idle footprint without models:** RSS **52 MB** after importing fastapi + pydantic + `quorum`
  (`torch` not in `sys.modules`).
- **F§10 — Loaded footprint:** cold load **29.5 s**; RSS **2.36 GB** after load, **3.9 GB** after the first
  6-label prediction (first inference 10.2 s incl. warm-up).
- **F§11 — Label-order invariance:** same message, permuted 6 labels → max |Δp| = **2e-9**, same top label.
- **F§12 — In-process unload is partial:** `del` + `gc.collect()` + `malloc_trim(0)` → RSS **748 MB**
  (second cycle **775 MB**). torch's native libs/arenas stay resident → in-process unloading cannot reach the
  ~100–200 MB target.
- **F§13 — Re-load after unload (same process):** **6.7 s** with model files in the OS page cache. NOTE: torch was
  already imported in that process, so this does NOT represent a freshly spawned worker — see F§14 for that.

- **F§14 — Spawned worker, real E2E (`serve/tests/test_real_e2e.py`, host load ~5, model files in page cache):**
  first miss (spawn child + import torch/transformers + load 3 models + first inference) **36.7 s**; cache hit
  **2.4 ms**; after the idle window the child exits and the API process RSS is **67 MB** with `torch` never imported.
  Repeat runs on the final code (warm-up job included, host load ~5): cold miss **81.7 s** and **89.8 s**; hit
  13–18 ms; API RSS 55–67 MB. → The first miss after an idle unload regularly exceeds the browser's 40 s abort
  (F§7); the server still completes and stores it, so a retry is a hit. 1.0b must handle the cold miss.
- **F§15 — Order invariance at K=77** (Banking77 names, 3 padded NLI batches;
  `measure/measure_order_invariance_big_k.py`): max |Δp| = **4.0e-9**, same top label.

## Consequences used by the spec

- A child-process inference worker that is terminated when idle is required to get idle RSS near F§9 (F§12).
- Cache keys may sort labels (F§11, F§15) — a permuted label list hits the same entry.
- The first miss after idle costs ~35–40 s (F§14): the idle window is a RAM-vs-latency trade-off (user decision),
  and the 1.0b frontend must tolerate a cold miss (the server stores the result even if the browser gives up, so a
  retry hits).
- The > 50 label rule must move from the Pydantic model into the handler so cache hits can bypass it (F§2).
